# タスク管理ガイド

## タスクとは

タスクは、Unit（オペレーションを実行するチーム）に割り当てる作業の単位です。タスクにはタイトル・説明・優先度などの情報を持ち、Unit のフェーズ設定と実行ランタイム（ワーカー種別・モデル・オーケストレーターモード）に従ってオーケストレーターにより自律的に実行されます。実行に使う Sidekick（タグ付きスキルパッケージ）はフェーズごとに Unit の `phase_config` で決まります。

## タスクの作成

### ワークスペースから作成

1. ワークスペースのアクティビティバーで **Tasks** モードを選択
2. 「+」ボタンをクリックすると、タスク作成用の専用フォームが Workspace のタブとして開く
3. 以下の項目を入力する

| 項目 | 説明 |
|---|---|
| Title | タスクのタイトル |
| Description | タスクの詳細な説明 |
| Project | 紐づけるプロジェクト |
| Assign to Unit | 実行する Unit（ワークフロー定義＋実行ランタイム）。プロジェクトの既定 Unit が事前選択される |
| Server Environment | 実行サーバーの上書き（プロジェクトに複数サーバーが紐づく場合に選択） |
| Priority | 優先度（数値、デフォルト: 0） |
| Plan Approval | 計画承認を必要とするかどうか |
| Base Branch | 作業ブランチの分岐元（省略時はリポジトリのデフォルト） |
| Target Branch | push / PR 作成時のターゲットブランチ |
| Issue Link | GitHub / GitLab のイシューをフォームから直接リンク（任意） |
| Skip PR | PR作成をスキップする（pushing時にコミット+プッシュのみ） |
| Branch | 作業ブランチ名（Skip PR 有効時に指定可能。既存ブランチがあればチェックアウト） |
| Working Directory | 作業ディレクトリ（プロジェクトのデフォルトを上書きする場合に指定） |

4. **Create** ボタンをクリック

> タスク作成/編集はモーダルではなく専用フォーム画面（タブ）で行います。キャンセル時は元のタスク一覧／詳細へ戻ります。

### GitHub / GitLab イシューからの作成

イシューからタスクをインポートすることもできます。詳細は [GitHub/GitLab 連携ガイド](./github-integration.md) を参照してください。

## ステータス一覧

タスクは以下のステータスを持ちます。

| ステータス | 説明 |
|---|---|
| `open` | 作成済み・未着手 |
| `running` | フェーズ実行中 |
| `phase_review` | フェーズ成果物のユーザー承認待ち（例: 計画承認） |
| `waiting_input` | エージェントが質問中・ユーザー回答待ち |
| `review` | 全フェーズ完了・最終レビュー待ち |
| `in_progress` | 実行中（follow-up 実行） |
| `done` | 完了 |
| `failed` | 失敗 |
| `archived` | アーカイブ済み（終端状態。tmux ウィンドウ等のリソースは解放済み） |

## 実行フロー

### UnitType 駆動フェーズループ

フェーズの順序は Unit の UnitType（TOML）で定義されます。デフォルトの `devops` タイプでは
planning → implementing → reviewing → testing → pushing の順に実行します。

```
open
  │
  ▼
running (phase N) ─────────────────────┐
  │                                    │
  ├─ planApproval → phase_review       │
  │                   │ approve        │
  │                   ▼                │
  │               running (phase N+1)  │
  │                                    │
  ├─ questions → waiting_input         │
  │                │ answer            │
  │                └───────────────────┘
  │
  ▼ (全フェーズ完了)
review → done  (または failed — 各フェーズから遷移可能)
```

## Worktree ベース実行

タスクの実行時に Git worktree を自動的に作成し、独立したブランチで作業を行います。

### 仕組み

1. タスク実行開始時に、プロジェクトのリポジトリに対して `git worktree add` を実行
2. ブランチ名: ユーザー指定がある場合はそのブランチ名、なければ `task/{id}-{slug}`（例: `task/42-add-login-page`）
3. worktree パスはタスクの `worktree_path` フィールドに記録
4. ワーカーはこの worktree ディレクトリ内で作業を行う

### メリット

- **正確な差分表示** -- メインブランチとの差分を正確に表示可能
- **分離実行** -- 他のタスクやメインブランチの作業に影響しない
- **並列実行との相性** -- 各タスクが独立した worktree で動作するため、並列実行時の競合を回避

### Worktree 作成失敗時の動作

worktree の作成に失敗した場合、タスクは `failed` ステータスに設定され、作成済みの tmux ウィンドウはクリーンアップされます。元のディレクトリで作業を続行するフォールバックは行いません（fail-fast）。

### 関連フィールド

| フィールド | 説明 |
|---|---|
| `worktree_path` | worktree のファイルシステムパス |
| `worktree_branch` | worktree のブランチ名 |
| `base_branch` | 分岐元のブランチ名（タスク作成時に指定可能） |
| `target_branch` | push / PR 作成時のターゲットブランチ（タスク作成時に指定可能） |
| `summary` | タスク完了時の実行サマリ（JSON形式） |
| `agent_session_id` | エージェントのセッションID（セッション復帰用） |
| `skip_pr` | PR作成スキップフラグ |
| `branch` | ユーザー指定の作業ブランチ名 |
| `working_directory` | タスク固有の作業ディレクトリ（プロジェクトサーバーのデフォルトを上書き） |

## プラン承認

`planApproval: true` が設定されたフェーズ（devops UnitType では planning）が完了すると、タスクは `phase_review` ステータスに遷移します。

### 承認フロー

1. ワーカーが実行計画を策定し、ログに出力
2. タスクが `phase_review` に遷移
3. タスク詳細画面に「Approve」と「Request Changes」のボタンが表示
4. **Approve** -- 計画を承認し、次のフェーズに進む
5. **Request Changes** -- コメントを添えて差し戻し。現在のフェーズに戻る

## 構造化質問 (QUESTIONS_JSON)

エージェントが実行中に確認が必要な事項がある場合、`QUESTIONS_JSON` マーカーで構造化された質問を出力します。

### 質問の形式

```json
AZITO_QUESTIONS_<taskId>_<nonce>: [
  {"text": "カンバンの列構成は？", "type": "select", "options": ["5列", "全個別"]},
  {"text": "追加の要望があれば", "type": "text"}
]
```

- `select`: 選択肢から1つを選ぶ形式
- `text`: 自由入力形式

### 回答フロー

1. エージェントが `QUESTIONS_JSON` を出力すると、タスクが `waiting_input` ステータスに遷移
2. タスク詳細画面に質問UIが表示される（セレクトボックス/テキスト入力）
3. ユーザーが回答を入力し「Submit Answers」をクリック
4. 回答がエージェントに送信され、タスク実行が再開
5. エージェントが追加の質問を出した場合、再度 `waiting_input` に遷移（ループ）

### 一意マーカー

フェーズごとに動的に生成されるマーカー（`AZITO_DONE_<taskId>_<nonce>`, `AZITO_QUESTIONS_<taskId>_<nonce>`）を使用し、プロンプトテンプレート内のマーカーとエージェントの実際の出力を確実に区別します。

## フォローアップ指示

実行中または一時停止中のタスクに対して、追加の指示（フォローアップ）を送信できます。

### 操作方法

1. タスク詳細画面の下部にあるコメント入力エリアにメッセージを入力
2. 必要に応じて**フェーズプロンプトチップ**を選択（Phase Prompt を添付）
3. 「Send」ボタンをクリック

フェーズプロンプトチップを使用すると、定義済みのフェーズプロンプト（例: 「テストを実行してください」「レビューしてください」等）をワンクリックで添付できます。フェーズプロンプトは Settings > Phase Prompts からカスタマイズ可能です。

## LLM セッション resume

タスクの実行中にサーバーの再起動やエラーが発生した場合、タスクを再開（resume）できます。

### 仕組み

1. タスク再開時に、既存の実行ログ（`execution_log`）から過去の会話内容を再構築
2. オーケストレーター LLM に会話履歴として送信し、セッションを復元
3. 中断した地点から実行を継続

これにより、長時間のタスク実行が中断した場合でも、コンテキストを失わずに作業を継続できます。

## 停滞検知とリトライ

タスクの実行中にワーカーの出力が一定時間変化しない場合、停滞として検知されます。

### 検知条件

- ワーカーの出力が **5分間** 変化しない場合に停滞と判定

### UI 表示

- タスク詳細画面に **警告バナー** が表示される
- 「This task appears to be stalled」のメッセージとともに **Retry** ボタンが表示

### リトライ

Retry ボタンをクリックすると、ワーカーに再度プロンプトを送信して実行を再開します。

## タスクのアーカイブと復帰

使い終わったタスクを削除せずにアーカイブし、必要になったら作業環境ごと復帰できます。

### アーカイブ

タスク詳細のメニューから **Archive** を選択すると、実行中であれば停止したうえで tmux ウィンドウ・window レコードなどのリソースをクリーンアップし、ステータスが `archived` になります。実行ログやタスク情報は保持されます。

### 復帰（Restore）

アーカイブ済みタスクのメニューから **Restore** を選択すると、worktree と tmux ウィンドウを再作成してステータスを `open` に戻します（既存の作業ブランチがあればそのままチェックアウト。失敗時はロールバック）。

- グローバルタスク一覧にはアーカイブ済みタスクのフィルターがあります
- アーカイブ済みタスクではステータスドロップダウンによる手動変更は無効化されます

## コミット履歴の表示

タスク詳細に **Commits** タブがあり、worktree のコミット履歴を確認できます。

- base branch からの差分コミット一覧（`base..HEAD`）を表示
- コミットを選択すると、そのコミット単体の diff を表示

## タスク削除とリソースクリーンアップ

タスクを削除すると、関連するリソースが自動的にクリーンアップされます。

- **tmux ウィンドウ** -- タスクに紐づく tmux ウィンドウを終了
- **Git worktree** -- タスク用に作成された worktree を削除
- **一時ファイル** -- pipe-pane の出力ファイルやシグナルファイルを削除

## セッション復帰

タスク実行中にエージェントのペイン（tmux ウィンドウ）が消失した場合、セッション復帰機能で作業を再開できます。

### 仕組み

- TaskPanel が30秒間隔でペインの生存を確認（`paneAlive` フラグ）
- ペインが消失すると、ステータス表示が「lost」に変わり、復帰ボタンが表示される
- 復帰ボタンをクリックすると、保存されたセッションID（`agent_session_id`）を使用してエージェントを再起動（`claude --resume <session-id>`）

## タスクサマリ

タスクが完了すると、実行結果のサマリが JSON 形式で自動抽出・保存されます。タスク詳細画面でサマリの内容を確認できます。

## PR 作成スキップ（Skip PR）

タスク作成時に「Skip PR」を有効にすると、pushing フェーズで PR の作成をスキップし、コミットとプッシュのみを行います。

- pushing プロンプトが「コミット+プッシュのみ、既存PRがあれば更新」に変化（`pushTaskDescription`, `pushRules`, `pushOutput` テンプレート変数で制御）
- 完了判定で PR の存在チェックをスキップ（SHA 一致のみで判定）
- ユーザー指定のブランチ名で worktree を作成可能（既存ブランチがあればチェックアウト）

## 作業ディレクトリの上書き

タスク作成時に「Working Directory」フィールドを指定すると、プロジェクトサーバーのデフォルト作業ディレクトリを上書きできます。

- worktree の作成、プロンプトテンプレート変数、push 完了確認など、すべての実行パイプラインでタスクの `workingDirectory` が優先される
- ブランチ検索もタスクの作業ディレクトリに連動（BranchInput コンポーネントが `working_directory` パラメータを API に送信）
- 未指定の場合はプロジェクトサーバーの設定値にフォールバック

## タスクログ

タスクの実行中に発生したすべてのイベントが実行ログとして記録されます。

### ログタイプ

| タイプ | 説明 |
|---|---|
| `llm_request` | オーケストレーターへの LLM リクエスト |
| `llm_response` | オーケストレーターからの LLM レスポンス |
| `command` | ワーカーへ送信したコマンド / プロンプト |
| `output` | ワーカーからの出力 |
| `status_change` | タスクステータスの変更 |
| `user_comment` | ユーザーからのフォローアップコメント |

### リアルタイムストリーミング

タスク詳細画面では、WebSocket（`task-logs` モード）を通じてログがリアルタイムにストリーミング表示されます。チャット形式の UI で、各ログエントリがタイプに応じたスタイルで表示されます。
