# コード配信（Issue #87）

## この文書の位置づけ

**コード配信**は、hub が自分の持つ git 資格情報を使って、対象サーバー上にプロジェクトのコードを
用意する仕組みです。サーバー側に git 資格情報を一切置かずに、そのサーバー上ですぐタスクを実行
できる状態を作ります。

もともとは[隔離実行プロファイル](./isolated-execution.md)（隔離サーバーは資格情報を持たないため、
コードの用意そのものが hub 側の代行でなければ成立しない）専用の機能でしたが、Issue #87 Phase 2
で隔離とは独立したオプトイン機能として一般化されました。本文書は配信の仕組みそのものを扱い、
隔離固有の話（3層モデル・isolation doctor・pushing フェーズの扱い等）は
[隔離実行プロファイル](./isolated-execution.md)を参照してください。

## 1. 適用範囲・有効化条件

配信が行われるかどうかは、タスク実行時にサーバーごとに次のルールで決まります。

| サーバー | 配信の有無 |
|---|---|
| `local`（hub 自身） | 対象外（常に配信しない）。hub 自身のサーバーへ「配信」する意味がないため |
| 隔離サーバー（`isolationIntent: true`） | **常に配信**。隔離サーバーは自力で clone するための資格情報を持たないため、オプトインの余地がない |
| 上記以外の `ssh`/`agent` サーバー | プロジェクト設定の配信オプション（既定オフ）を有効化した場合のみ配信 |

非隔離サーバー向けの配信オプションは、設定 → プロジェクト → サーバー環境の追加/編集フォームで、
作業ディレクトリの入力欄の下にあるトグルから有効化します（既定オフ）。用途は、hub 側に作業用の
チェックアウトや開発ツールチェーンを持たせず、エージェントサーバー側だけで開発する運用です
（hub は git 資格情報自体はプロジェクトのために保持し続けます。リポジトリの代行 fetch にその
資格情報が必要なためです）。hub はタスク実行・監視などの hub 機能に専念します。

いずれの場合も配信には SSH が必要です。`agent` 型サーバーであっても SFTP 転送のために SSH 接続
情報（`sshHost` 等）の設定が前提になります。SSH が使えないサーバーへの配信はエラーとして失敗
します（サイレントにスキップされません）。

## 2. 仕組み

配信は、タスク実行のウィンドウ作成後・worktree 作成前のタイミングで、対象サーバー×リポジトリ
ごとに直列化されて実行されます（同じサーバー×リポジトリへの同時配信はキューされ、mirror への
書き込みが競合しません）。

### 2.1 hub 側キャッシュ

hub は認証済みの bare リポジトリキャッシュを `$AZITO_DATA_DIR/repo-cache/<repoHash>` に持ちます。
`repoHash` はリポジトリの正規化された URL から決定的に導出される値で、hub 側キャッシュとサーバー
側 mirror（後述）の両方が同じリポジトリに対して同じハッシュを使います。配信のたびに、hub は
プロジェクトに設定された資格情報でこのキャッシュを対象ブランチだけ fetch し、最新化します。

### 2.2 サーバー側 bare mirror

配信先サーバーには、リポジトリごとの配布専用 bare mirror を `~/.azito/repos/<repoHash>.git` に
用意します（未作成なら初回配信時に `git init --bare` で作成）。この mirror はタスクが直接作業する
場所ではなく、配信内容の受け皿専用です。

### 2.3 bundle 転送・検証・取り込み

hub は hub 側キャッシュから `git bundle create` で bundle を作成し、**SFTP でサーバーへ転送**し
ます。サーバー側では受け取った bundle を `git bundle verify` で検証したうえで、mirror へ
`git fetch --atomic` で取り込みます。取り込みの refspec は強制（`+refs/heads/<branch>:
refs/heads/<branch>`）です — 上流が force-push されていても non-fast-forward で失敗せず、次回
配信で回復します。

### 2.4 増分配信とその起点

2回目以降の配信は、可能であれば増分 bundle（前回配信済みのコミットからの差分のみ）を作ります。
ここが設計上のポイントです: **増分配信の起点（prerequisite）は DB に記録された「前回配信 SHA」
ではなく、mirror が実際に受信済みの ref を毎回問い合わせて決めます**。DB の記録は観測用の
キャッシュに過ぎず、correctness の根拠にはしていません。これにより、mirror が手動で消された、
あるいは上流が force-push されて祖先関係が変わった、といった DB と実体のずれが起きても、次回の
配信が自己修復します（増分の作成・検証・取り込みが失敗した場合は、1回に限り全量 bundle へ
自動的に切り替えて再試行します）。

### 2.5 作業ディレクトリの用意

mirror への取り込みが終わったら、タスクの作業ディレクトリ（`workingDir`）を用意します。

- 未作成なら、mirror から `git clone --no-local --branch <branch>`（ローカル clone の hardlink
  最適化は mirror の並行更新と競合しうるため `--no-local` 必須）でローカル clone します。
- 既に存在するなら、mirror を source に指定して `git fetch` で更新します。ただしこの更新は
  **追跡 ref（`refs/remotes/origin/<branch>`）だけを強制更新し、ローカル branch ref には触れ
  ません**。ローカル branch を書き換える方式だと、その branch がリンク worktree で
  チェックアウトされている場合（タスクのブランチ指定がベースブランチ名と同じ場合など）に
  fetch 自体が失敗し、以後そのサーバー×リポジトリへの配信が永続的に失敗し続けるためです。
  更新後の内容を必要とする側（後述のタスク worktree 作成）は `origin/<branch>` を明示的に
  参照します。
- 作業ディレクトリの HEAD は毎回 detach します（clone 直後・fetch 更新後のどちらでも冪等に
  適用）。作業ディレクトリは人が作業する場所ではなく配信の受け皿であるため、branch を掴んだ
  ままだと後続のタスク worktree 作成（同名 branch を割り当てる場合）が失敗するのを防ぎます。
- 作業ディレクトリの `origin` リモート URL は**ダミー URL**（`.invalid` ドメイン）に設定されます。
  サーバーから上流リポジトリへの直接アクセスは意図的に失敗する構成であり、以後の更新は必ず
  mirror 経由（上記の fetch）で行われます。

### 2.6 タスクの worktree

タスクの worktree は、配信で更新された作業ディレクトリを起点に作成されます。配信が実際に何かを
届けた（新規配信、または既に最新だった）場合、worktree 作成のベースブランチは `origin/<ベース
ブランチ>` を明示的に参照します（作業ディレクトリのローカル branch は上記のとおり更新されない
ため、ローカル branch をそのまま使うと古い内容になり得るからです）。

## 3. 残存リスク（隔離の限界）

サーバー側の bare mirror は、**タスクと同一の Unix ユーザー権限の下に**置かれます。タスクは
元々そのユーザーとして任意コード実行が可能なため、mirror がタスクと同じ権限下にあること自体は
権限昇格ではありません。しかし、タスクが mirror の `refs`/`objects`/`config` を直接書き換え、
次回配信時に汚染された内容を作業ディレクトリ・以後のタスク worktree へ伝播させたり、配信自体を
妨害したりする余地は残ります。現状の対策は、mirror に触れる git 実行すべてに
`-c core.hooksPath=/dev/null` を付けて hook の実行だけを防ぐところまでで、mirror の所有権を
タスクの実行ユーザーから分離する対策は行っていません。この点は隔離実行の限界の一つとして
認識しておいてください。

## 4. ネットワーク要件

配信には hub からサーバーへの SSH 接続が必要です（SFTP は SSH のサブシステムのため）。隔離
サーバーでこの機能を使う場合のファイアウォール設定は[隔離実行プロファイルのネットワーク隔離
節](./isolated-execution.md#6-ネットワーク隔離横移動対策)を参照してください — inbound で
`agentPort` に加えて SSH ポートを許可する必要があります。
