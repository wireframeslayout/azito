# issue-default -- イシュー作成スキル

ユーザーの要望をヒアリングし、**sonnet級の自律エージェントがそのまま実装に着手できる詳細度** のイシューを作成する。

（harness/skills/azt-issue/SKILL.md はこのパッケージを取得して従う薄いラッパー。実装手順の本体はここ。）

## 引数

- 引数（任意）: イシューの概要テキスト。省略時はユーザーに対話でヒアリングする。

## Step 0: コードベースの調査

イシュー本文の精度を上げるため、**イシューに関連するコードを必ず先に調査する**。

- 対象の機能がどのファイルに実装されているかを特定する（grep, find）
- 変更対象のコードを読み、現在の実装を理解する（Read）
- 関連するDB スキーマ、API エンドポイント、フロントエンドコンポーネントを把握する
- 類似の既存実装パターンがあれば確認する

この調査結果を Step 2 の「実装手順」に反映する。

## Step 1: 要件のヒアリングと明確化

ユーザーが提供した情報（引数またはメッセージ）から、以下を整理する。
情報が不足している場合は AskUserQuestion で質問する（最大2回まで）。

整理する項目:
- **何を作る/直す/変える**: 対象の機能・コンポーネント・振る舞い
- **なぜ必要か**: 動機・背景（バグなら再現手順、機能なら利用シーン）
- **完了条件**: 何が達成されたら Done か（検証可能な条件）
- **スコープ外**: 明示的にやらないこと（あれば）

ヒアリングで得た情報が十分であれば、次のステップへ進む。
**過剰な質問はしない。** ユーザーが十分な情報を提供している場合はそのまま進む。

## Step 2: イシュー本文を構成する

以下のテンプレートに従い、Markdown 形式でイシュー本文を作成する。
**sonnet級エージェントが実装に着手できるレベルの具体性** を持たせること。

### 詳細度の基準

イシュー本文は以下の基準を満たすこと:
- **ファイルパス**: 変更対象のファイルを具体的に列挙する（例: `packages/server/src/application/ExecuteTaskUseCase.ts`）
- **行番号の目安**: 変更箇所の行番号を記載する（例: L142-175）
- **コード例**: 変更内容を示すコードスニペットを含める（擬似コードではなく実際のコード）
- **既存パターン**: 類似の実装が既にあればそのファイル・パターンを参照として示す
- **DB 変更**: マイグレーションが必要な場合、バージョン番号・カラム名・型を明記する
- **依存関係**: 他のイシューへの依存がある場合は明示する

### テンプレート

```markdown
## 概要
（1-2文で変更の目的を述べる）

## 背景・動機
（なぜこの変更が必要か。バグなら再現手順、機能なら利用シーン）

## 要件
- [ ] （検証可能な完了条件をチェックリストで列挙）

## 実装手順
### 1. （手順名）
**ファイル**: （パス）
（変更内容の説明 + コードスニペット）

### 2. ...
（以降同様）

## スコープ外
（この Issue では対応しないこと。なければ省略）
```

**「技術メモ」ではなく「実装手順」を書く。** 参考情報の羅列ではなく、エージェントが上から順に実行できるステップバイステップの手順を記載する。

作成したイシュー本文をユーザーに提示し、内容の確認を取る。

## Step 3: 登録先を判定して登録する

### 3a. リポジトリの判定（GitHub → GitLab → azito タスクの順にフォールバック）

```bash
gh repo view --json url -q '.url' 2>/dev/null
```

- コマンドが成功し URL が返れば **GitHub Issue** として登録する（Step 3b）
- 失敗した場合、次に GitLab を試す:
  ```bash
  glab repo view 2>/dev/null
  ```
  - こちらが成功すれば **GitLab Issue** として登録する（Step 3b-gitlab）
  - こちらも失敗した場合は **azito タスク** として登録する（Step 3c）

### 3b. GitHub Issue を作成する

```bash
gh issue create --title "<タイトル>" --body "$(cat <<'ISSUE_EOF'
<イシュー本文>
ISSUE_EOF
)"
```

作成された Issue URL をユーザーに報告する。

### 3b-gitlab. GitLab Issue を作成する

```bash
glab issue create --title "<タイトル>" --description "$(cat <<'ISSUE_EOF'
<イシュー本文>
ISSUE_EOF
)"
```

作成された Issue URL をユーザーに報告する。

### 3c. azito タスクとして登録する

環境変数 `AZITO_URL`（デフォルト: `http://localhost:3001`）を使用する。

1. プロジェクト一覧を取得し、ユーザーに登録先プロジェクトを選択させる:
   ```bash
   curl -sf -H "Authorization: Bearer ${AZITO_UI_TOKEN}" "${AZITO_URL:-http://localhost:3001}/api/projects"
   ```

2. Unit 一覧を取得し、担当 Unit を選択させる:
   ```bash
   curl -sf -H "Authorization: Bearer ${AZITO_UI_TOKEN}" "${AZITO_URL:-http://localhost:3001}/api/units"
   ```

3. タスクを作成する:
   ```bash
   curl -sf -X POST -H "Authorization: Bearer ${AZITO_UI_TOKEN}" "${AZITO_URL:-http://localhost:3001}/api/tasks" \
     -H "Content-Type: application/json" \
     -d '{"project_id": <id>, "unit_id": <id>, "title": "<タイトル>", "description": "<イシュー本文>"}'
   ```

作成されたタスクIDをユーザーに報告する。

## 注意事項

- イシューのタイトルは **動詞で始める**（例: 「追加する」「修正する」「リファクタする」）
- 本文の「要件」は、実装者が **コードを読まなくても着手できる** レベルの具体性を目指す
- ユーザーが既に十分な情報を提供している場合、追加質問なしで Step 2 に進んでよい
- ラベルやマイルストーンの設定は求めない（シンプルに保つ）
